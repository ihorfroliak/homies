# FE-003 synthetic engagement fixtures

Authorized by HOMIES-DELIVERY-002, FE-003 scope. These are fictional accounts,
listings, conversations and appointments for a disposable development database.
They are not imported product data or a production initializer.

## Invocation

Run migrations and `python -m app.scripts.seed_e2e` first. Then, from `backend/`:

```sh
HOMIES_ALLOW_E2E_SEED=1 HOMIES_ALLOW_ENGAGEMENT_E2E_SEED=1 \
  python -m app.scripts.seed_engagement_e2e --manifest "$RUNNER_TEMP/homies-engagement-manifest.json"
```

The original seed's explicit development `ENV` and disposable database name
(`*_e2e`, `*_test`, `*_ci`) remain mandatory, alongside both opt-ins. Every
check runs before database/file access. The manifest's parent directory must
already exist. Keep it in runner temporary storage, never `public/`, browser
bundles, console output or published CI artifacts. It contains only synthetic
user credentials and opaque fixture IDs; no administrator credentials/tokens.
Linux creates it with owner read/write permissions.

Frontend Node tests consume `E2E_ENGAGEMENT_MANIFEST`. Use
`manifest.projects[project.name]` where the configured project is `desktop` or
`mobile`. Send only the selected test user's credentials through the normal
login interface. Never pass the entire manifest to page code.

## Manifest version 1

Top-level fields: `version: 1`, `locality_id`, `projects.desktop`, `projects.mobile`.
Each project has the following maps:

| Map | Keys and meaning |
| --- | --- |
| `accounts` | `seeker` (no verified contact), `phone_seeker`, `restricted_seeker` (verified phones), `provider` (host, verified root), `unverified_provider` (host, active unverified root on its own listing), `guest_provider` (guest role, scoped mandate from verified provider), `host_without_authority` (host role alone) |
| `listings` | `approval`, `instant`, `phone`, `held`, `restricted`, `closed`, `redacted`, `past_requested`, `past_confirmed`, `unavailable`, `unverified` |
| `conversations` | `approval`, `restricted`, `closed`, `redacted`, `unverified` |
| `viewings` | `held`, `restricted`, `past_requested`, `past_confirmed`, `unverified` |
| `messages` | same keys as conversations: provider USER reply IDs; plus `reportable` (alias of approval reply), `closed_system`, `restricted_system` |

Every account entry is `{email, password}`. All other map values are opaque IDs.
Names and emails are deterministic, prefixed `FE003 <project>` and
`fe003-<project>-`; IDs are generated by the real API and captured in the file.
`seeker` is the requester for all pre-created threads/viewings except
`restricted`, whose requester is `restricted_seeker`.

- `approval` and `instant` offer public, weekly derived slots every day, 10:00–16:00
  in Europe/Warsaw. The slot API supplies actual instants and timezone to tests.
- `held` has a future REQUESTED viewing, then a listing moderation hold without
  close-engagement. It is unavailable publicly; the authorized provider can read
  the pending request and confirmation is blocked.
- `restricted` has a prior successful phone reveal, a thread and future requested
  viewing before a real G-14 moderation decision. The thread closes, viewing is
  cancelled by HOMIES and repeat phone reveal returns RECONTACT_BLOCKED.
- `closed` has a real closure SYSTEM line. `redacted` has a removed provider USER
  reply whose participant projection has null body; its thread remains ACTIVE.
- `past_requested` remains REQUESTED, and `past_confirmed` remains CONFIRMED.
  They support time-based controls/outcome tests without inventing EXPIRED.
- `unavailable` was saved by `seeker` before provider pause. Its saved projection
  is a tombstone with no cached listing details.
- `unverified` has real engagement established before the synthetic verification
  withdrawal. Its owner is denied private engagement; requester access persists.

## Isolation, repeat runs and limitations

Lublin is a separate geographic seed source. The original twelve listings
(ten Kraków, two Warszawa), titles, owners, discovery ordering within those
cities and default seed invocation are unchanged. Only optional contact fields
were added to the original listing helper, retaining its original defaults.

Desktop/mobile have separate users, properties, listings and engagement rows.
Within one project, each mutating scenario must have one owning test; use fresh
random registered requesters for independent save/start/request journeys. Do not
run several tests that mutate the same pre-created thread/viewing concurrently.
A retry of a consumed scenario needs a recreated database, not a silent reset.

A repeated seed invocation requires the same completion manifest. It verifies
inventory identities and actual projections, then returns without recreating
fixture rows or replacing the file. Authentication creates normal refresh-token
rows. Missing/invalid manifests, incomplete namespaces and changed required
states fail explicitly; no automatic delete/reset/repair is attempted. A failed
initial run has no completion manifest and must be recreated on a disposable
database. The fixture is for short-lived E2E runs: future pre-created appointments
are three days ahead, and past appointments two days behind creation.

## Exact synthetic setup boundary

Accounts, identities, publication/authority verification, scopes via mandate,
schedules, derived-slot requests, messages, phone confirmation, saves, pause,
moderation/redaction and cancellation all use existing in-process HTTP API routes.
The seed captures the verification channel in memory instead of sending SMS;
actual code issuance and confirmation still execute. Rate limiting is disabled
only in that process and restored on exit, as with the standard seed.

Two fixture-only database edits have no equivalent current API:

1. The two past scenarios are created through normal viewing requests, then their
   viewing start/end/created/response timestamps are shifted together into history.
   Their original creation event timestamps are not rewritten. These are explicit
   synthetic lifecycle fixtures, not historical event replay evidence.
2. The `unverified` listing owner's root is changed from VERIFIED to UNVERIFIED
   while remaining ACTIVE, after real conversation/viewing creation. Revocation
   would exercise a different authorization condition and pause the listing.

No production business code, migration, authority rule or moderation rule is
changed. Administrative bootstrapping comes only from the existing guarded
standard seed. Browser tests never receive administrative credentials.
